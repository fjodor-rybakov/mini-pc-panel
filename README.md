# s1panel — переписано с Node.js на Go

Go-демон для AceMagic S1 LED-TFT панели (VID `0x04D9`, PID `0xFD01`): экран 320×170
по HID (интерфейс MI_01) + LED-подсветка по CH340 (последовательный порт).
Переписан с оригинального Node.js-проекта `mini-pc-panel` строго по протоколу
из [`doc/revrite.md`](doc/revrite.md) (§2), плюс браузерный редактор виджетов
телеметрии. Оригинальное Node.js-приложение, snap- и Node-Docker-сборки и
картинки удалены из репозитория 2026-11-19 — проект существует только как это
Go-переписывание (всё удалённое — в истории git).

## Структура

```
./ (корень репозитория)
├── cmd/s1panel/main.go      демон: флаги, сигнал SIGINT/SIGTERM, запуск цикла и админки
├── cmd/ledctl/main.go       диагностика ленты: один LED-кадр прямо в CH340 (make ledctl)
├── internal/config/         config.json + тема экранов (валидация, дефолты, сохранение)
├── internal/display/        протокол HID (пакеты) + очередь/один воркер (10 мс пауза)
├── internal/led/            CH340: пакет FA|theme|intensity|speed|checksum
├── internal/metrics/        сенсоры: gopsutil + /sys/class/hwmon (temp/power)
├── internal/render/         tdewolff/canvas → RGB565 big-endian, виджеты, PNG превью
├── internal/app/            склейка: жизненный цикл, ротация экранов, превью на реальный экран
├── internal/server/         HTTP-админка: редактор + API (embed web/)
├── Dockerfile               docker-сборка: 2 этапа (cgo+hidapi → debian-slim)
├── docker-entrypoint.sh     засев config.json/тем в том при первом запуске
├── docker-compose.yml       запуск с доступом к USB-шине (libusb) и CH340
├── config.example.json      пример конфигурации (значения = дефолты кода)
└── themes/demo.json         демо-тема (2 экрана, сеточные координаты)
```

## Сборка (Linux — целевая платформа)

Требуется cgo: `gcc`, `libhidapi-dev` (backend hidraw) или `libusb-1.0-0-dev`
(backend libusb), `make`.

```sh
make build         # backend hidraw, bin/s1panel
make build-libusb  # backend libusb (-tags libusb), bin/s1panel-libusb
make ledctl        # bin/ledctl — диагностика ленты (один кадр прямо в порт)
make test vet fmt  # тесты, vet, gofmt
```

**Какую панель какой бэкенд берёт:** оригинальное Node.js-приложение
работало только через libusb (`node_hid.setDriverType('libusb')`,
`lcd_thread.js:14`), и Docker-сборка повторяет это — `go build
-tags libusb`. У прошивок новых ревизий screen-интерфейс объявляет в
report-дескрипторе output-отчёт меньше кадра (наблюдалось 512 бит для
4104-байтных пакетов); ядро через hidraw запись большего размера
отвергает, так что на хосте для таких панелей — `make build-libusb`.
Для панелей оригинальной ревизии работает и hidraw-сборка.

`github.com/sstallion/go-hid` — cgo-библиотека, поэтому кросс-сборка с Windows
не работает (на Windows собирается только stub-транспорт, остальные пакеты и
тесты проходят: `go test ./...`).

## Запуск

```sh
cp config.example.json config.json   # поправить sensors/fonts под машину
./bin/s1panel -config config.json              # адрес админки — из конфига "listen"
./bin/s1panel -config config.json -admin :8080 # -admin перебивает "listen"; -admin "" — выкл
```

### Docker

```sh
docker build -t s1panel .
docker compose up -d --build   # готовый вариант с devices/volumes
```

При первом запуске в том `/etc/s1panel` засевается `config.json` (из
`config.example.json`) и каталог `themes/`. Образ собран с libusb-бэкендом,
поэтому hidraw-узлы панели контейнеру не нужны — нужен доступ к USB-шине
(compose: монтирование `/dev/bus/usb` + `device_cgroup_rules: c 189:* rwm`,
см. `docker run`-пример в шапке `Dockerfile`) и подсветке
`--device /dev/ttyUSB0`. Хостовые
датчики видны как есть (`/sys/class/hwmon` в контейнере read-only), а
`sensors.mount_points` меряет монтирования внутри контейнера — конфиг под
контейнер обычно стоит поправить.

Жизненный цикл (spec §5.3): `set_orientation` → `set_time` → полный `redraw`,
далее heartbeat по правилу оригинала (не чаще раза в секунду: занятая очередь —
порог `heartbeat` (по умолчанию 60000 мс), простой — порог `redraw_delay`) и
опрос тикером: шлются только изменившиеся плитки (`update` 0xA2, ≤2048
пикселей на пакет; дифф считается по плиткам, а не по виджетам — тикающие
секунды часов меняют пару плиток, а не весь регион) либо весь кадр. Регион
нарезается на минимальное число пакетов (полоса 300×6 — это 2 пакета, а не
7), изменённые плитки кадра идут одним job без разрывов; если изменившихся
плиток ≥27, partial заменяется полным `redraw` — его 27 чанков пишутся
слитно, как в `redraw_next` оригинала. Паузами между пакетами и после
redraw управляют `packet_delay` и `redraw_delay`.

### udev (доступ без root)

`/etc/udev/rules.d/99-s1panel.rules`:

```
SUBSYSTEM=="usb", ATTRS{idVendor}=="04d9", ATTRS{idProduct}=="fd01", MODE="0660", GROUP="plugdev"
SUBSYSTEM=="hidraw", ATTRS{idVendor}=="04d9", ATTRS{idProduct}=="fd01", MODE="0660", GROUP="plugdev"
KERNEL=="ttyUSB*", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", MODE="0666"
```

Первая строка нужна libusb-сборке (доступ к `/dev/bus/usb/…`), вторая —
hidraw-сборке.

```sh
sudo udevadm control --reload-rules && sudo udevadm trigger
sudo usermod -aG plugdev $USER   # перелогиниться
```

Прошивки панелей различаются: у оригинальных экран сидит на HID-интерфейсе
MI_01 (`:1.1` — так и было в оригинальном `config.json`: `"device":
"1-8:1.1"`), у других ревизий интерфейсы панели — это `:1.0` и `:1.2`
(узла MI_01 нет вовсе). Демон справляется сам: если заданного `interface`
нет в перечислении, он по sysfs определяет, какой интерфейс панели —
экранный: только у него в report-дескрипторе есть output-отчёт (у кнопок
его нет), и открывает этот интерфейс уже своим бэкендом — hidraw или
libusb (`internal/display/report_desc.go`). Важная оговорка: новые
прошивки занижают размер output-отчёта в дескрипторе (наблюдалось 512 бит
при рабочих 4104-байтных кадрах), поэтому hidraw-сборка на них открывает
узел, но не может записать кадр — нужен libusb-бэкенд (`make build-libusb`,
в Docker он уже по умолчанию), ровно как в оригинале
(`setDriverType('libusb')`). Вручную интерфейс закрепляется прямо в
конфиге: `"device": { "path": "…" }` — формат пути зависит от бэкенда
(hidraw: `/dev/hidrawN`; libusb: путь из перечисления, его печатает строка
`iface N at <путь>` в логе ошибки); при заданном `path` `vid`/`pid`/
`interface` в поиске не участвуют.

### systemd

`/etc/systemd/system/s1panel.service`:

```ini
[Unit]
Description=AceMagic S1 panel daemon
After=multi-user.target

[Service]
ExecStart=/opt/s1panel/bin/s1panel -config /etc/s1panel/config.json -admin 127.0.0.1:8080
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

## Диагностика ленты: ledctl

Если лента не слушается демона, `ledctl` шлёт один кадр прямо в порт тем же
кодом `internal/led`, что и демон (побайтовая пауза 5 мс), минуя конфиг,
редактор и цикл экранов — это делит проблему на «демон ничего не шлёт» и
«лента не реагирует»:

```sh
make ledctl
./bin/ledctl list                 # перечислить порты; CH340 = VID=1a86 PID=7523
./bin/ledctl off                  # FA 04 05 05 08 — сначала остановите демон
./bin/ledctl -port /dev/ttyUSB1 rainbow -i 3 -s 3
```

Тот же `ledctl` лежит в docker-образе (в контейнере порт всегда
`/dev/ttyUSB0`):

```sh
docker compose stop
docker compose run --rm --entrypoint ledctl s1panel list
docker compose run --rm --entrypoint ledctl s1panel off
docker compose up -d
```

- Перед запуском остановите демон (`docker compose stop` / `systemctl stop
  s1panel`), чтобы порт был свободен.
- Если `ledctl list` показал CH340 под другим номером, чем `/dev/ttyUSB0`:
  поправьте `led.port` в конфиге, а в docker задайте узел хоста переменной
  `LED_DEVICE` — в `docker-compose.yml` теперь
  `- ${LED_DEVICE:-/dev/ttyUSB0}:/dev/ttyUSB0`, то есть
  `LED_DEVICE=/dev/ttyUSB1 docker compose up -d --build`. Сам демон тоже
  ищет CH340 (VID `1a86`) среди видимых портов: если `led.port` не CH340
  или отсутствует, а CH340 ровно один — открывается он, и это пишется в лог.
- Если `ledctl off` ленту погасил, а демон — нет: сравните
  `journalctl -u s1panel | grep led` (или `docker compose logs s1panel | grep led`)
  с действиями редактора. Демон теперь пишет при старте `led: opened <порт>
  (VID=... PID=...)` и список всех видимых портов, а при каждой отправке —
  кадр целиком (`led: frame FA 04 05 05 08 -> /dev/ttyUSB0`,
  `led: manual frame ...`). Нет строки `frame` — демон кадр не шлёт (порт
  не открыт или стоит режим theme 6 «ignore»); строка есть, а лента горит —
  кадр уходит не в то устройство (проверьте `LED_DEVICE` / `led.port`).
- Если `ledctl off` ленту не погасил — к демону претензий нет: питание
  панели, кабель, сам CH340.

Ручное «выкл» из редактора сохраняется на диске: каждый «применить LED»
пишет `theme/intensity/speed` в живой конфиг контейнера
`panel-data/config.json` (он засевается из `config.example.json` только при
первом запуске, поэтому правки `config.example.json` потом ни на что не
влияют) — ровно так же делал оригинальный GUI (`api.js set_led_strip`).
Значит «выкл» переживает `docker compose restart`/redeploy, а если CH340
в момент команды недоступен, режим всё равно записан и применится при
следующем старте (ответ редактора содержит `"saved": true|false`). Если
нужно задать режим руками: `"led": { "port": "/dev/ttyUSB0", "enabled":
true, "theme": 4 }` в `panel-data/config.json`, затем `docker compose restart`.

## Standby: ночное отключение экрана

В протоколе HT32 нет команды выключения питания/подсветки
(`doc/revrite.md` §2), поэтому «полное отключение» программное:
полный redraw чёрным кадром, LED-лента в off, обновление виджетов
останавливается. Подсветка матрицы продолжит светиться (аппаратно её
погасить нельзя), но картинка чёрная, а шина молчит.

Расписание — блок в `config.json` (оба поля обязательны, формат
`"HH:MM"`; `start > end` — окно через полночь; блока нет или он пуст —
standby выключен):

```json
"standby": { "start": "23:00", "end": "07:00" }
```

Таймер настраивается прямо в редакторе, править `config.json` руками не
нужно: внизу страницы чекбокс «таймер» и два поля времени
(`POST /api/standby/schedule`). Включение чекбокса сохраняет окно в
`panel-data/config.json` (переживает перезапуск), выключение очищает блок
`standby` — таймера нет вовсе, и тогда экран гаснет **только кнопкой**
«экран выключен»: ни расписание, ни границы его обратно не включают.
Кнопка работает и при активном таймере
(`POST /api/standby?on=true|false`); граница расписания перекрывает ручной
выбор на ближайшем тике — в том числе сразу после смены окна в редакторе.
Состояние кнопки и таймера отдаёт `GET /api/state` в полях `"standby"` и
`"standby_schedule"`.

Окно полуоткрытое `[start, end)`: в 23:00 экран гаснет, в 07:00 —
полная перерисовка и восстановление LED. Границы ловятся на каждом
`poll`-тике; старт демона внутри окна тоже сразу отдаёт чёрный первый
кадр (без вспышки живого экрана). Heartbeat панели (раз в секунду)
продолжается всегда — иначе микроконтроллер «зависает» экран. «Примерить
на экран» во время standby панель не будит: картинка в браузере отдаётся,
но на экран ничего не уходит (в логе «app: preview not pushed: standby is
on»); раньше превью перекрашивало чёрный кадр живым — экран казалось «не
выключается».

## Протокол (коротко, полностью — doc/revrite.md §2)

Каждый HID-командный пакет ровно **4104 байта** (8 заголовков + 4096 payload,
обнулённый хвост); на `dev.Write` уходит **4105** — ведущий `0x00` Report ID
добавляет только транспорт (`transport_linux.go`), внутри пакет остаётся 4104.

| команда | заголовок |
|---|---|
| orientation | `55 A1 F1 o` (01 = 320×170, 02 = 170×320) |
| heartbeat / set time | `55 A1 F2|F3 h m s` |
| redraw | `55 A3 sub seq off len` (заголовок в двух раскладках — см. ниже), 27 чанков × 4096 (последний 2304) |
| update | `55 A2 x_lo x_hi y_lo y_hi w h`, `w*h*2 ≤ 4096` |

### ⚠ Дуальность заголовка redraw (важно)

Оригинальный JS (`lcd_device.js:103-105`) писал offset/length **big-endian** в
байты 5..6/7..8, а копирование payload в `p[8]` затирало младший байт длины.
Спецификация §2 описывает «правильный» little-endian вариант. Реализованы оба:

- `DefaultRedrawLayout = RedrawOriginalLayout` — байт-в-байт как в JS
  (включая затирание `p[8]`); это раскладка по умолчанию — оригинал доказал её
  на реальном железе;
- `RedrawSpecLayout` — «правильный» little-endian вариант из §2 (длина в
  `p[6:8]`), тоже реализован.

Если доверяете §2, поменяйте константу в `internal/display/protocol.go` —
тесты `TestRedrawPacketsSpecLayout` и `TestRedrawOriginalLayoutQuirk`
фиксируют обе раскладки.

## Редактор виджетов (PART B)

Открыть `http://<host>:8686` — адрес берётся из `"listen"` в конфиге (флаг
`-admin :PORT` перебивает его, `-admin ""` отключает редактор). Vanilla JS,
без сборки.

- **Сетка**: мелкие линии каждые 10 px, крупные каждые 50 px, координаты под
  курсором; привязка к сетке (шаг 5/10/20) включается кнопкой «привязка к сетке».
- Виджеты: `text`, `doughnut`, `doughnut_chart`, `line_chart`, `bar_chart`,
  `custom_bar`, `image`, `spacer`; у экрана — поле `wallpaper` (фон-картинка
  на весь экран, режим cover); drag — мышью, resize — поля свойств.
- Цифры в редакторе **реальные**: `GET /api/poll` раз в секунду тянет те же
  показания, что рисует демон.
- **«Примерить на экран»** — `POST /api/preview?screen=N`: черновик валидируется
  (`config.ParseTheme`), рендерится и отправляется **на физический экран**
  (полный redraw + LED экрана), в ответ приходит PNG того, что теперь показывает
  панель; тишина опроса на время показа превью.
- **Живое превью «как видит экран»** — `POST /api/render?screen=N`: та же
  валидация и рендер, но **без касания панели**; редактор обновляет картинку
  в футере (родные 320×170) дебаунсом в 500 мс после любой правки — картинка
  больше не появляется только после «Применить».
- **«Применить»** — хот-своп живой темы (`POST /api/apply`), `?save=1` пишет
  `theme_file`; «Сохранить и применить» — то же с сохранением.
- LED вручную: тема/яркость/скорость (тема 1..6, в редакторе 1..5) →
  `POST /api/led` (CH340, контрольная сумма = сумма первых 4 байт & 0xFF).
  Как оригинальный `led_device.js`, кадр отправляется побайтно с паузой
  5 мс между байтами — прошивка ленты отбрасывает плотный burst, и полоса
  остаётся в прежнем режиме (в том числе не гаснет от `off`).
  Отправленные настройки становятся живым глобалом и пишутся в `config.json`
  (как в оригинале — см. «Диагностика ленты»): ротация экрана их не
  откатывает, но `led_config` конкретного экрана по-прежнему перебивает их,
  а «выкл» переживает перезапуск демона.
- **Живое переключение тем** (как дропдаун оригинального GUI): `GET /api/themes`
  отдаёт `theme_list` + текущий `theme_file`, `POST /api/theme {"file":…}` или
  `{"name":…}` грузит тему из списка на живую; `config.json` на диске не
  трогается. В редакторе — селектор «тема» в шапке.
- **Экраны**: `POST /api/next_screen` — сразу следующий включённый экран, тело
  `{"id":N}` прыгает на экран с этим id; `POST /api/pause?on=true|false` —
  пауза/возобновление ротации. В редакторе — кнопки «Следующий экран» и
  «пауза ротации» в футере.

## Тесты

`go test ./...` — 7 пакетов, всё зелёное: байтовые спецификации всех четырёх
команд (обе раскладки redraw), целостность redraw перед heartbeat в одном
воркере, clamps и контрольные суммы LED, дефолты/отказы конфига и темы, hwmon
на фейковой sysfs, RGB565/format-токены/регионы и пиксельные замки виджетов,
целостность блоков partial-update, минимальную упаковку SplitRect,
слитные чанки redraw и слив устаревших заданий очереди,
весь HTTP-редактор (включая `/api/themes`, `/api/theme`, `/api/next_screen`,
`/api/pause`) через `httptest` и фейковый `Panel` (без железа).

## Отличия от оригинального JS (осознанно)

- Погодная подсистема вычеркнута целиком: оригинальное Node.js-приложение
  `s1panel/` (виджеты `weather`/`weather_icon`/`winddirection`, иконки
  iconify) удалено из репозитория, а сами эти типы виджетов больше не
  принимаются валидацией темы.
- Оригинальный массив `sensors` в `config.json` игнорируется: набор сенсоров
  Go собирает сам из блоков `sensors.*` (clock, calendar, cpu, memory,
  space_<mount>, net_<iface>_rx/tx, temp, power).
- Heartbeat — как в оригинале, по порогам (`heartbeat` при занятой очереди,
  `redraw_delay` при простое) и не чаще раза в секунду (§5.2); «строго раз
  в 1 с» не реализовано намеренно.
- Защита от затыка ссылки и «экран обновляется полосками, одна половина
  запаздывает на полсекунды». Симптом — стрим плиток внутри одного кадра:
  панель малюет каждую плитку по мере прихода (пакет + 10 мс), и когда
  тик требует десятки плиток, дальние регионы дорисовываются через
  ~0.5 с. Лечится сокращением числа пакетов: дифф на уровне плиток
  (не виджетов), минимальная упаковка `SplitRect` вместо сетки 45×45,
  все плитки кадра одним job, а при ≥27 изменённых плитках — один слитный
  полный `redraw` (27 пакетов с той же паузой между чанками, что и у
  partial-потока: полевым проверкой на HT32 этой ревизии подтверждено, что
  чанки без пауз доезжают целиком (в дебаг-сборке это логировалось строкой
  «display: redraw: all 27 chunks on the wire», сейчас убрано как шум) —
  но панель их не latch'ит, экранный кадр не меняется; паузованный redraw
  работает) вместо десятка partial-пакетов. Плюс backpressure
  из первого раунда: пока в очереди есть незаписанные задания, очередной
  частичный кадр в очередь не попадает (в оригинале main.js ждёт от
  lcd-воркера `complete` перед следующей отправкой); редизинк для
  ресинхронизации выбрасывает устаревшие частичные задания из очереди
  (heartbeat/orientation сохраняются). В логе: строка «app: display
  pacing v4 ...» при старте (признак новой сборки), «app: panel link
  behind ...» (не чаще раза в минуту) и «dropping N stale queued update
  job(s)». Если затык повторяется — увеличить `packet_delay` (пауза
  между partial-пакетами, по умолчанию 10 мс) в `config.json`.
- Стартовый `set_time` (F3) демон шлёт по §5.3 — оригинал F3 не использовал.
- LED при смене экрана: оригинал откатывался к `theme||4`; здесь нулевые поля
  `led_config` экрана наследуют глобальные настройки — блок `led` конфига
  (5/3/3), а если из редактора уже отправляли LED вручную, то ручные
  настройки (до перезапуска демона). Режим 6 («не трогать») пакет не шлёт —
  как в `led_thread.js`. При штатной остановке демон шлёт `off`, если сам
  управлял лентой: контроллер CH340 запоминает последний режим, и иначе
  лента продолжала бы гореть и при `led.enabled: false`.
- Линейные графики — ломаные без слаживания (в оригинале canvas tension 0.1);
  `image`/`wallpaper` обрезаются геометрически вместо canvas-клипа; пути
  картинок разрешаются относительно файла темы.
- Переключение темы из редактора живое и не пишет `config.json`; сохранение
  темы в файл — только «Применить» с галкой.
- Нет инвертированного UI `fix_value`.
- API админки своё (см. выше); форма оригинального Electron-UI не
  воспроизводилась — тема, экраны и пауза ротации доступны прямо в редакторе.
- `cpu_power` по RAPL: читаются только верхневые зоны `intel-rapl:N`
  (подзоны `intel-rapl:N:M` не суммируются дважды), переполнение
  `energy_uj` корректируется по `max_energy_range_uj`, а дельта энергии
  всегда делится на фактический интервал между сэмплами — оригинал делил
  лишь «примерно раз в секунду», поэтому показания могут немного
  отличаться. Если RAPL нет, hwmon-фолбэк перебирает чипы по приоритету
  (`coretemp, k10temp, zenpower, rapl, cpu_thermal, acpitz, nvme`) —
  чип `rapl` это hwmon-представление RAPL в новых ядрах; мощность NVMe
  больше не попадёт в `cpu_power`. В Docker учтено отдельно: он маскирует
  `/sys/devices/virtual/powercap`, и без mount'а этого каталога RAPL-зон в
  контейнере не видно — датчик давал `cpu_power: N/A`. В `docker-compose.yml`
  каталог примонтирован на **неканонический** путь `/powercap` (часть версий
  Docker перекладывает маску поверх mount'а на исходном пути), а датчик при
  поиске зон перебирает корни `/sys/class/powercap`, `/powercap` и
  `/powercap/intel-rapl`.
- Валидация конфига строгая: `vid`/`pid` — целые в диапазоне 0..65535
  (обрезки не будет), относительные пути тем не могут выходить за каталог
  конфига, `led.theme` 1..6 и `led.intensity`/`led.speed` 1..5,
  дубликаты id экранов и виджетов отвергаются. Конфиги, которые раньше
  грузились «с глюком», теперь падают с внятной ошибкой.
- Цветовые цепочки виджетов приведены к редактору: `line_chart`,
  спарклайн `doughnut_chart` и `bar_chart` уважают `color` (поле
  «цвет» в редакторе), но `outline`/`fill` по-прежнему приоритетнее.
  Штатные полоски `bar_chart` толщиной 1 px рисуются без обводки —
  штрих шириной 1 px заливал бы соседние полоски.
- `doughnut_chart` рисует кольцо слева и график истории справа — как
  его же превью в редакторе (_go-рендер ранее рисовал только кольцо);
  кольцо в широком виджете теперь прижато к левому краю, а не центрировано.
